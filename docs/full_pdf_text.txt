Key Questions & Technical Analysis 
Q1: What is the difference between Continuous Integration and Continuous Deployment, and 
which one does this practical actually demonstrate? 
Answer: Continuous Integration (CI) is the practice of automatically integrating code changes from multiple 
developers into a shared repository several times a day. Each integration is verified by an automated build and 
test suite to detect integration bugs as quickly as possible. Continuous Deployment (CD) is the next phase, 
where code that passes all automated tests is automatically packaged (e.g., Docker containerized) and deployed 
directly into production environments without human intervention. This practical specifically implements and 
demonstrates Continuous Integration (CI), as the GitHub Actions pipeline automates dependency installation, 
linting, and automated Jest API testing on every push and pull request, reporting a pass/fail verification status. 
Q2: Why does running tests automatically on every push catch problems earlier than testing 
manually before a release? 
Answer: Manual testing conducted shortly before a release suffers from extensive latency and large changeset 
scope. When a bug is discovered in a multi-week release cycle, developers must sift through hundreds of 
commits to locate the root cause, leading to expensive debugging delays and release postponements. In 
contrast, automated CI testing on every push creates an immediate feedback loop: any regression is isolated to 
the specific commit or pull request that introduced it (within 40 seconds). This drastically lowers the cost of 
fixing defects, prevents bad code from compounding across team branches, and ensures the main branch 
remains perpetually deployable. 
Q3: What would happen to the pipeline if the test file path were incorrect—would the workflow fail 
at the same step as a genuine test failure? 
Answer: If the test file path is incorrect or missing, the workflow will still fail at the exact same step (Run 
Automated Tests / npm test), because Jest exits with a non-zero exit code when no matching test files are 
discovered or if a syntax error prevents test compilation. However, the diagnostic output in the GitHub Actions 
runner log differs fundamentally: a genuine test failure outputs a detailed assertion diff (e.g., Expected: 200, 
Received: 500) pointing to a specific line in the test file, whereas a file path error outputs 'No tests found' or 
'Cannot find module'. Both halt the pipeline, but require distinct troubleshooting approaches.

Conclusion 
In this practical, an automated Continuous Integration (CI) pipeline was successfully designed, implemented, and 
verified for the full-stack Task Management application using GitHub Actions, Node.js, Express.js, Jest, and 
Supertest. 
 
Key development milestones and findings achieved include: 
1. Automated Workflow Architecture: Created .github/workflows/ci.yml configured to trigger automatically on 
every push and pull request targeting the main branch. 
2. Multi-Job Pipeline: Implemented a two-stage job pipeline comprising code quality/syntax validation (lint) and 
automated API test execution (build-and-test) running on ubuntu-latest. 
3. Automated API Test Suite: Authored comprehensive Jest/Supertest suites validating root health endpoints, input 
validation middleware (400 Bad Request rejection), and event diagnostics with 100% pass rate. 
4. Empirical Fault Diagnosis: Deliberately induced a test assertion mismatch (broken.test.js), demonstrating the 
pipeline immediately catching the defect, halting execution with exit code 1, and displaying a Red X failure on 
GitHub. 
5. Regression Correction: Fixed the assertion error, demonstrating the pipeline turning green (exit code 0) and 
updating the dynamic README status badge to passing. 
6. Frontend CI Observability: Embedded an interactive PipelineModal in TaskFlow Pro, allowing developers to 
inspect real-time runner metadata, job execution durations, and step logs. 
 
All practical objectives, supplementary problems, and architectural analyses were successfully implemented, tested, 
and validated.
